## 一、指令

当我平时折腾电脑时，总是看到AI或者一些小文章提到ping,curl，但并不知道区别，只浅显得知用于网络测试连接
当我复习到计网的ICMP时（其实是第一次学了一遍），看到书上关于ping，traceroute（unix指令）的测试指令，想到了我在nixos上常用到的curl，并好奇，遂探究

| 工具                       | 探针流量               | 靠什么回显                        | 测的是       | 教材对应               |
| ------------------------ | ------------------ | ---------------------------- | --------- | ------------------ |
| `ping`                   | **ICMP echo** 请求   | 目的主机回 echo 应答（type 0）        | IP 层连通性   | ICMP 回显请求/应答       |
| `tracepath`/`traceroute` | **UDP** 探针（TTL 递增） | 路由器回 ICMP「时间超过」；目的主机回「端口不可达」 | 逐跳路径      | TTL 机制 + ICMP 差错报告 |
| `curl`/浏览器（URL）          | **TCP**（HTTPS 443） | 目标 Web 服务器回 HTTP 应答          | 传输层+应用层可达 | 端口/TCP/HTTP        |

## 二、通——tracepath www.bilibili.com

```fish
 1:  _gateway                    4.5 毫秒
 2:  172.255.0.34                4.0 毫秒
 3:  120.195.18.5                7.8 毫秒
 4~7: 无应答
 8:  111.1.63.194               19.8 毫秒
11:  112.13.92.203              19.6 毫秒  到达
```

**机制**：

1. 工具从 **TTL=1** 开始发 UDP 探针；
2. 第 1 台路由器收到 TTL=1 的包 → **TTL 减 1 变成 0 → 丢弃，并回 ICMP「时间超过」**——工具凭回包的源 IP 得知「第一跳是谁」；
3. TTL=2、3、… 依次递增 → 每一跳都「被迫自报家门」；
4. 直到探针到达目的主机：主机**不转发、不把 TTL 减 1**，但 UDP 探针打在没人监听的端口上 → 回 **ICMP「端口不可达」**——工具据此判定「到达」；
5. 每行一个时间：`tracepath` 每 TTL 发一个探针（`traceroute` 发 3 个，教材说「每一行有三个时间」）。

**「无应答」不等于包丢了**：第 4~7 跳的探针其实经过了那几台路由器，只是它们**不响应 ICMP**（运营商不回应 ICMP 探测）——所以工具显示沉默，但路径是通的（第 8 跳又出声了）。

## 三、ping www.baidu.com——`ttl=53` 

```fish
64 字节，来自 36.152.44.93: icmp_seq=1 ttl=53 时间=8.19 毫秒
--- 已发送 6 个包，已接收 6 个包，0% packet loss
```

```
应答中的 TTL = 目的主机发出时的初始值 − 回程经过的跳数
Linux 默认初始 TTL = 64   →   64 − 53 = 11 跳（回程）
```

与实验 1 的去程 11 跳几乎一致——**去回程对称**，两个工具互相印证。若初始值是 128（Windows）或 255（部分设备），算法相同、减数不同。

其他细节：`56(84) 字节` = 56 数据 + 28 首部（IP 20 + ICMP 8）——ICMP 报文嵌在 IP 数据报里的实物证据。

## 四、外网（youtube）的连接测试（终端环境已开启代理）

### 3.1 tracepath：UDP 探针 30 跳无应答

```fish
 1: _gateway   2.2 毫秒
 2~5: 正常（有「不对称」标记）
 6~30: 全部无应答
30: Too many hops
```

探针在路径某处被**静默丢弃**（不回 ICMP 时间超过）→ 工具等不到「下一跳是谁」→ 30 跳封顶放弃。

### 3.2 ping：DNS 解析成功，但 ICMP 100% 丢包

```fish
PING www.youtube.com (185.45.5.35) ...
--- 已发送 20 个包，已接收 0 个包，100% packet loss
```

**最有教学价值的一行**：域名**解析成功了**（拿到了 IP），ICMP 却全丢。

**DNS 能解析 ≠ 能连通**。「通」是分层的：解析（应用层）✅、IP 路由 ❌（黑洞）、ICMP 回显 ❌。

### 3.3 curl -I：TCP 隧道里，HTTP 响应回来了

```fish
HTTP/1.1 200 Connection established     ← 代理服务器的应答
HTTP/2 200                              ← youtube 真身的应答
```

**两层响应**：curl 走 HTTP 代理时，先向代理发 `CONNECT www.youtube.com:443`（请求建隧道）→ 代理回 `200 Connection established`；隧道内 curl 与 youtube 做 TLS 握手并协商 HTTP/2 → youtube 回 `200`。

## 五、和教材的关联

### 5.1 TTL

- 每过一台路由器 **TTL − 1**；减到 **0 → 丢弃 + 回 ICMP「时间超过」**；
- tracepath 就是**故意**让包死在每一跳，靠 ICMP 差错报告反向测绘路径；
- TTL 防止数据报在网络中无限循环。

### 5.2 ICMP

| 报文                   | 谁发   | 语义         | 实验里的角色          |
| -------------------- | ---- | ---------- | --------------- |
| echo request / reply | 主机互发 | 连通性测试      | ping 的载体        |
| 时间超过                 | 路由器  | TTL 减到 0   | tracepath 认跳    |
| 终点不可达（端口）            | 目的主机 | 无法交付/端口无监听 | tracepath 认「到达」 |

**ICMP 差错报文本身可能被防火墙过滤**——所以「无应答」可能是「不通」，也可能只是「对方闭嘴」。

### 5.3 黑洞

某些设备/防火墙对特定目标**不回任何 ICMP、也不报错**，直接丢弃——表现为探测工具一路无应答。这是网络层「尽力而为」的另一面：**没有回显不代表没有到达，到达了也不保证回显**。

### 5.4 分层连通性

```
DNS 解析  ✅（youtube 能出 IP）
IP 路由  ❌（直连黑洞）
ICMP 回显 ❌（ping loss）
TCP 连接 ✅（走代理隧道后）
HTTP 响应 ✅（curl 200）
```

**每层独立**：上层通不保证下层通，下层通也不保证上层通；排查问题先定位「断在哪一层」。

### 5.5 代理 = TCP 隧道，只管 TCP

- HTTP/SOCKS 代理、分流客户端：**只接管 TCP**（浏览器/curl 走隧道）；
- **ICMP（ping）、UDP（tracepath 探针）不在代理服务范围** → 开不开代理它们都直连 → 结果一样（100% loss / 无应答）；
- 所以「ping 不通」不能证明代理失效——**验证代理看 TCP（curl/浏览器），验证直连看 ICMP/UDP**；
- youtube 响应头 `alt-svc: h3=":443"` 表示它也支持 **HTTP/3（QUIC，跑 UDP 443）**——若浏览器切到 HTTP/3，流量又变成 UDP、脱离 TCP 隧道，所以代理环境下常回退 HTTP/2。
